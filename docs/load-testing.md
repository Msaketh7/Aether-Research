# Aether Research: Load Testing

> **The rule that governs this document is the one that governs
> [`evaluation.md`](evaluation.md): no number appears here unless a run
> produced it.** Every figure below was generated by `make loadtest` or
> `make loadtest-api-local` on the machine named in §2, and the raw artefact is
> committed at [`data/loadtest/results.json`](../data/loadtest/results.json).
> Nothing is extrapolated, rounded up, or carried over from a previous run.

## 1. What is being loaded, and why it is two things

There are two ceilings in this system and they are reached for different
reasons, so there are two load tests.

| Arm          | Tool                              | Question                                                                       |
| ------------ | --------------------------------- | ------------------------------------------------------------------------------ |
| **Pipeline** | `apps/api/scripts/loadtest.py`    | How much research does a worker get through when _n_ jobs are offered at once? |
| **Surface**  | `apps/api/loadtest/locustfile.py` | What does the API cost a person while all of that is outstanding?              |

The split follows [ADR 0001](ADRs/0001-modular-monolith.md). The API never runs
a research graph; it validates, persists, enqueues and returns `202`. The whole
architecture rests on the claim that a saturated worker does not make the
product unresponsive, and that claim is only testable by loading both ends and
looking at them together.

```bash
make loadtest              # the pipeline: provisions its own Postgres, needs no credentials
make loadtest-api-local    # the surface: stands up a disposable API and loads it
make loadtest-api HOST=https://staging.example.com   # the surface, against a deployment
```

## 2. Conditions

Read these before reading any number below. A throughput figure without its
conditions is not a fact about anything.

| Condition       | Value                                                                                                                                                                        |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Measured        | 2026-09-18                                                                                                                                                                   |
| Machine         | Intel i5-13420H, Windows 11, Python 3.13. **The CPU runs at roughly a third of nominal and never turbos.**                                                                   |
| Real            | Postgres, the job queue, the lease, the LangGraph graph, all nine agents, the toolbelt behind its SSRF guard, ingestion, retrieval, the evidence projection, report assembly |
| Scripted        | The **model provider**, behind the real gateway, answering in 0.5 s; the **socket**, behind the real guarded client                                                          |
| Queue           | In-memory adapter (`APP_ENV=test`) - Redis is not installed on this machine                                                                                                  |
| Retrieval       | Lexical arm only - no pgvector on this machine                                                                                                                               |
| Worker capacity | One process, `worker_concurrency=4`, held constant across all four loads                                                                                                     |

**Why the model is scripted.** A load test that made real model calls would
measure a vendor's queue rather than this system's, would cost hundreds of
dollars per profile, and would not be reproducible. So provider latency becomes
an _input_ - declared at 0.5 s per call, printed beside every number it
produced, and deliberately lower than a real structured call, which is seconds.
It is not zero, because a run that never awaits gives another run nothing to
overlap with: concurrency would buy nothing and the queueing behaviour these
profiles exist to find would not occur.

**Read these as ratios, not as capacity.** The absolute figures belong to a
throttled laptop CPU. What transfers is the _shape_: which curve is flat, which
one bends, and which resource ran out first.

## 3. Pipeline: throughput and completion

Four loads, one worker with four execution slots, each profile starting from an
empty database.

| Profile     | Offered | Capacity | Wall (s) | Completed | Completion rate | Runs/min  |
| ----------- | ------- | -------- | -------- | --------- | --------------- | --------- |
| offered-10  | 10      | 4        | 26.8     | 10        | 100.0%          | 22.38     |
| offered-25  | 25      | 4        | 44.6     | 25        | 100.0%          | 33.67     |
| offered-50  | 50      | 4        | 80.5     | 50        | 100.0%          | 37.25     |
| offered-100 | 100     | 4        | 152.9    | 100       | 100.0%          | **39.25** |

**Nothing was lost and nothing failed**, at any load. 185 research runs, 185
completions, each with its sources ingested, its claims extracted and verified,
its report assembled and its citations validated.

Throughput _rises_ with offered load and flattens at about 39 runs/min. That is
not a scaling gain: the four slots are the same four slots. It is the ramp
disappearing into the average - in a 27-second profile, the tail in which fewer
than four slots are busy is a large fraction of the run; in a 153-second one it
is not. The asymptote, about 39 runs/min, is this machine's real capacity at
four slots.

## 4. Pipeline: latency

| Profile     | Stage         | P50 (s)  | P95 (s)  | P99 (s) | max (s) |
| ----------- | ------------- | -------- | -------- | ------- | ------- |
| offered-10  | total         | 20.89    | 26.29    | 26.53   | 26.59   |
|             | queue wait    | 14.55    | 20.91    | 21.15   | 21.21   |
|             | execution     | 6.60     | 14.17    | 14.20   | 14.20   |
| offered-25  | total         | 25.32    | 39.51    | 43.29   | 44.49   |
|             | queue wait    | 19.15    | 32.81    | 37.73   | 39.29   |
|             | execution     | 6.18     | 7.74     | 7.87    | 7.90    |
| offered-50  | total         | 44.42    | 75.90    | 80.25   | 80.27   |
|             | queue wait    | 38.53    | 69.85    | 73.67   | 73.78   |
|             | execution     | 6.14     | 7.09     | 7.16    | 7.19    |
| offered-100 | total         | 81.70    | 146.30   | 152.65  | 152.67  |
|             | queue wait    | 75.84    | 140.63   | 146.24  | 146.25  |
|             | **execution** | **6.11** | **7.06** | 7.14    | 7.15    |

**This is the most important table in the document, and the column to read is
`execution`.** It does not move. A research run takes about 6.1 seconds at the
median whether ten jobs are outstanding or a hundred; its P95 is 7.1 s at a
hundred, _lower_ than at ten. The run itself does not get slower as the system
fills up.

Everything that grows is queue wait, and it grows linearly with the backlog -
14.5 s, 19.2 s, 38.5 s, 75.8 s. That is a system that is **queueing, not
degrading**, which is the behaviour the architecture was chosen for. A system
that degraded instead would show execution latency climbing with load, and the
fix for that is different: it would mean the runs were contending with each
other rather than waiting for a slot.

The one anomaly is `offered-10`'s execution P95 of 14.2 s against a 6.6 s
median. That is the process's remaining cold start - the first runs through pay
for imports and connections that every later run finds warm. `warm_up()` in the
driver pays LlamaIndex's four and a half seconds before the first profile is
timed, but not everything.

## 5. Pipeline: what ran out first

Instantaneous readings every 0.25 s, so a spike shorter than that is a spike
this did not see.

| Profile     | Peak queue depth | Peak running | Slots saturated | Peak db in use | Peak db overflow | Peak LLM calls in flight |
| ----------- | ---------------- | ------------ | --------------- | -------------- | ---------------- | ------------------------ |
| offered-10  | 10               | 4            | 77%             | 5              | 0                | 4                        |
| offered-25  | 25               | 4            | 88%             | 5              | 0                | 4                        |
| offered-50  | **665**          | 4            | 99%             | 5              | 0                | 4                        |
| offered-100 | **4662**         | 4            | 100%            | 5              | 0                | 4                        |

Three answers and one defect.

**The worker's execution slots ran out, and nothing else did.** At 100 offered
jobs the four slots were busy in 100% of samples. That is the ceiling.

**The database is nowhere near it.** Peak occupancy was 5 connections against a
pool of 10 with 5 of overflow available, and the overflow was never touched at
any load. Adding database capacity would buy nothing here.

**The model-concurrency ceiling is not binding either.** Of 1,480 model calls
across the four profiles, **zero** waited for a gateway slot; peak in-flight was
4 against a limit of 8.

| Profile     | Slot limit | Model calls | Calls that queued | Mean wait (s) | Max wait (s) |
| ----------- | ---------- | ----------- | ----------------- | ------------- | ------------ |
| offered-10  | 8          | 80          | 0.0%              | 0.0000        | 0.000        |
| offered-25  | 8          | 200         | 0.0%              | 0.0000        | 0.000        |
| offered-50  | 8          | 400         | 0.0%              | 0.0000        | 0.000        |
| offered-100 | 8          | 800         | 0.0%              | 0.0000        | 0.000        |

Four runs execute at a time and each makes its calls in sequence, so the process
never asks for more than four of its eight slots. Raising
`llm_max_concurrent_calls` would change nothing. The lever is worker
concurrency, or a second worker.

### The defect: queue depth amplifies under a backlog

**Peak queue depth reached 4,662 entries for 100 offered jobs**, and 665 for 50.
Ten and twenty-five, which drain inside the grace period, show exactly the
number offered.

The cause is the reconciliation sweep in
[`app/workers/loop.py`](../apps/api/app/workers/loop.py). Every sweep asks
Postgres which runs _should_ be on the queue - and a run that is still `queued`
because the worker is busy answers yes, every single time, for as long as the
backlog lasts. Neither the sweep nor the queue deduplicates, so each sweep adds
up to `worker_sweep_batch` entries that are already there.

Nothing is executed twice: claiming a run is a conditional update, and the
duplicate delivery is dropped. What breaks is the measurement, and it breaks in
the place where it matters most:

- **`queue_depth` is the metric on the Grafana dashboard**, and it is the
  obvious signal for scaling workers. Reading 4,662 when 100 jobs are
  outstanding is wrong by a factor of 46, and an autoscaler driven by it would
  be driven off a cliff.
- **Under Redis, the list grows without bound** for as long as the backlog
  lasts, rather than being merely inaccurate.
- The worker spends reserve round trips on stale ids. At this scale it costs
  little - throughput still rose from 50 to 100 - but the work is pure waste.

This is why load testing exists: the sweep is covered by tests, all of which
pass, and the scenario suite drives it fifteen ways. None of them holds a
backlog open for longer than the grace period, because none of them offers more
work than the worker can take. **It is fixed and re-measured in Phase 22**,
where it is the first measured optimisation.

## 6. Surface: the HTTP API under load

Locust, against a disposable stack: a throwaway Postgres, a migrated schema and
one uvicorn process. Each simulated user registers its own account, because
every read on this surface is scoped by `user_id` and by identity for rate
limiting - users sharing an account would share one index entry and one token
bucket, and would measure contention no deployment has.

The development identity is switched off for the run
(`DEV_IDENTITY_ENABLED=false`). In `test` it answers any request that arrives
without a session, so a load whose sign-in was broken would keep returning
`200`s while silently measuring one shared user. That is not hypothetical: it
is what the first run of this file did, and closing the gate is what caught it.

### The ladder

Four loads: 20 users over 60 s, then 25, 50 and 100 over 45 s each, spawning at
10 a second. Each figure is Locust's own, from a separate disposable stack.

| Users | Requests | Failures | Agg P50 (ms) | Agg P95 (ms) | `GET /research` P50 | `GET /research/stats` P50 | `GET /health` P50 |
| ----- | -------- | -------- | ------------ | ------------ | ------------------- | ------------------------- | ----------------- |
| 20    | 352      | 0        | 40           | 160          | 39                  | 38                        | 8                 |
| 25    | 194      | 0        | 45           | 790          | 49                  | 43                        | 10                |
| 50    | 286      | 1        | 37           | 720          | 40                  | 37                        | 9                 |
| 100   | 460      | 0        | 45           | 610          | 45                  | 49                        | 9                 |

**The read surface does not degrade.** From 20 users to 100, `GET /research`
moves between 39 and 49 ms at the median, `GET /research/stats` between 37 and
49 ms, and the aggregate P50 stays at 37-45 ms. Five times the users, the same
latency. The request rate rose with the load (4.9 to 11.1 req/s) and was bounded
by the generator's own think time, not by the server - which is the honest
reading: **this ladder did not find the surface's ceiling.** It found that the
ceiling is above 100 concurrent readers on one uvicorn process on a throttled
laptop.

**The whole tail is one endpoint, and it is meant to be there.**

| Users | `POST /auth/register` P50 (ms) | P95 (ms) | Max (ms) |
| ----- | ------------------------------ | -------- | -------- |
| 20    | 72                             | 1500     | 1468     |
| 25    | 780                            | 2900     | 2916     |
| 50    | 410                            | 2700     | 2727     |
| 100   | 170                            | 2200     | 2556     |

Registration is Argon2id at the shipped parameters - about 130 ms of deliberate
CPU per hash, run in a thread so it does not stall the event loop. Spawning 25
users in 2.5 seconds queues 25 of those in the thread pool, and the queue is the
P50. It is the only endpoint in the product designed to be slow, and the
aggregate P95 column above is essentially a measure of it. Strip registration
out and every remaining P95 in the ladder is under 400 ms.

**Liveness never failed; readiness failed once.** `GET /health` answered in
8-10 ms at every load, including while 100 users were registering. `GET /ready`
returned `503` once, on the 50-user run, in the opening burst - it really checks
Postgres, and 50 simultaneous registrations each holding a connection is enough
to make that check wait.

That is the two probes doing exactly what they are separated for
([`app/api/v1/health.py`](../apps/api/app/api/v1/health.py)): the load balancer
is told to stop sending traffic for a moment, and the orchestrator is _not_ told
to restart the container. Worth noting rather than fixing blind: one failed
readiness check in forty-five is also the shape that makes a replica flap, and
whether the pool should be larger than 10+5 for an API that authenticates is a
question for a deployment's sizing, not for this measurement.

## 7. What these numbers do not tell you

Stated plainly, because a load test's credibility is mostly its disclaimers.

- **Nothing here measures a real model provider.** Its throttling, its tail
  latency and its failure modes are all outside this measurement. What is
  measured is the system around it, with the provider held at a declared
  constant.
- **Redis is not measured.** There is no Redis on this machine, so the
  in-memory queue adapter was used. Queue depth, lease behaviour and
  reconciliation are all real; Redis's own utilisation is _not measured_, not
  zero.
- **Dense retrieval is not measured.** Without pgvector, ingestion stores chunks
  with their vectors pending and retrieval runs its lexical arm only. A
  deployment with the dense arm does more work per run than anything here.
- **One worker process.** Everything above is a single process's ceiling. The
  multi-worker behaviour - two workers sweeping, competing for the same lease -
  is covered by the scenario suite but has not been load tested.
- **The absolute numbers are this laptop's.** See §2.

## 8. Reproducing this

```bash
make loadtest                          # writes data/loadtest/results.{json,md}
make loadtest ARGS="--profile offered-25"
make loadtest ARGS="--offered 8 --concurrency 2 --model-latency 0"
make loadtest-api-local USERS=50 RUNTIME=45s
```

The profiles are declared in
[`apps/api/app/loadtest/profiles.py`](../apps/api/app/loadtest/profiles.py) and
asserted against this document's four loads by
`apps/api/tests/test_loadtest.py`, so dropping one fails the build rather than
quietly shrinking the test.
